# Structured data in 2026

## What still earns rich results

Google has been steadily retiring rich result types it considers low-value, so recommending schema requires knowing what's still live. Current state:

**Still generating rich results — prioritize these:**
- `Product` (with `Offer`, `AggregateRating`) — the highest commercial value type, and increasingly load-bearing for AI shopping surfaces
- `Review` / `AggregateRating` — star ratings
- `Article` / `NewsArticle` / `BlogPosting`
- `BreadcrumbList`
- `VideoObject`
- `Event`
- `Recipe`
- `LocalBusiness` and its subtypes
- `Organization` — no visual rich result, but it's the backbone of entity understanding
- `JobPosting`, `SoftwareApplication`, `Dataset`, `Book`, `Course` (feature support varies by region and vertical — verify against Google's current documentation before promising a specific appearance)

**Retired or effectively dead:**
- `FAQPage` — FAQ rich results stopped appearing in Google Search on **7 May 2026**. Search Console reporting and Rich Results Test support were removed in June 2026; Search Console API support ends August 2026.
- `HowTo` — desktop rich results removed in 2023; practical value now minimal.
- Retired in June 2025: Book Actions, Course Info, Claim Review, Estimated Salary, Learning Video, Special Announcement, Vehicle Listing.

## The FAQ deprecation

Worth explaining properly, because the user will have questions about it and there's a lot of confused advice circulating.

What changed: the SERP feature. What didn't: `FAQPage` is still a valid Schema.org type, Google still parses it to understand pages, and unused structured data does not harm Search. So there is no urgency to strip it out — and no reason to add it hoping for a rich result.

The practical guidance:
- **Keep the FAQ content.** Well-written questions with direct answers are exactly the format answer engines extract. The content was always doing the work; the schema was never doing it.
- **Treat the markup as optional.** Leave it if it's there, don't build new tooling around it, and stop measuring it.
- **Update reporting pipelines** before August 2026 if anyone is pulling FAQ data from the Search Console API — those calls will start returning nothing.
- Note that `QAPage` is a different type, for pages where users submit competing answers, and is unaffected.

## Rules that actually matter

1. **Markup must match visible content.** This is the rule people break most and the one that gets structured data ignored or penalized. Schema describing a rating, a price, or an FAQ that doesn't appear on the page is a spam signal. Google's own guidance on AI features says the same thing: no special schema is needed, but whatever you use must reflect what's actually on the page.
2. **JSON-LD in the head or body**, not Microdata. It's Google's stated preference and it's far easier to maintain.
3. **Present in the server response.** Schema injected by client-side JS or a tag manager is picked up inconsistently. This is one of the more common silent failures.
4. **One block per entity, no duplicates.** A page with two conflicting `Article` blocks — one from the theme, one from an SEO plugin — can be disqualified entirely. On WordPress especially, check for plugin-vs-theme collisions.
5. **Required properties present.** A type missing its required properties simply doesn't qualify.
6. **Link entities with `@id`.** This is the difference between a pile of disconnected blocks and a coherent graph the machine can traverse.
7. **Validate.** Google's Rich Results Test for eligibility, Schema.org's validator for correctness. They answer different questions.

## Templates

### Organization (site-wide, on the homepage)

The entity anchor. Everything else references it.

```json
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "@id": "https://example.com/#organization",
  "name": "Example",
  "url": "https://example.com",
  "logo": {
    "@type": "ImageObject",
    "url": "https://example.com/logo.png",
    "width": 512,
    "height": 512
  },
  "description": "One clear sentence about what the company actually does.",
  "foundingDate": "2019-03-01",
  "address": {
    "@type": "PostalAddress",
    "streetAddress": "…",
    "addressLocality": "İstanbul",
    "addressRegion": "İstanbul",
    "postalCode": "34349",
    "addressCountry": "TR"
  },
  "contactPoint": {
    "@type": "ContactPoint",
    "telephone": "+90-212-000-0000",
    "contactType": "customer support",
    "availableLanguage": ["Turkish", "English"]
  },
  "sameAs": [
    "https://www.linkedin.com/company/example",
    "https://x.com/example",
    "https://github.com/example"
  ]
}
```

`sameAs` is the load-bearing property for entity resolution — list every authoritative profile the organization genuinely controls.

### Article / BlogPosting

```json
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "@id": "https://example.com/blog/slug/#article",
  "headline": "Under 110 characters, matching the visible H1",
  "description": "…",
  "image": ["https://example.com/img/cover.jpg"],
  "datePublished": "2026-06-14T09:00:00+03:00",
  "dateModified": "2026-07-02T11:30:00+03:00",
  "author": {
    "@type": "Person",
    "@id": "https://example.com/yazarlar/ad-soyad/#person",
    "name": "Ad Soyad",
    "url": "https://example.com/yazarlar/ad-soyad/"
  },
  "publisher": { "@id": "https://example.com/#organization" },
  "mainEntityOfPage": { "@type": "WebPage", "@id": "https://example.com/blog/slug/" }
}
```

Note the author as a linked `Person` entity rather than a bare string — that's what carries expertise signals, and it's the single most common upgrade available on an existing implementation.

### Product

```json
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "…",
  "image": ["…"],
  "description": "…",
  "sku": "…",
  "brand": { "@type": "Brand", "name": "…" },
  "offers": {
    "@type": "Offer",
    "url": "https://example.com/urun/slug/",
    "priceCurrency": "TRY",
    "price": "1299.00",
    "availability": "https://schema.org/InStock",
    "priceValidUntil": "2026-12-31",
    "shippingDetails": { "@type": "OfferShippingDetails", "…": "…" },
    "hasMerchantReturnPolicy": { "@type": "MerchantReturnPolicy", "…": "…" }
  },
  "aggregateRating": {
    "@type": "AggregateRating",
    "ratingValue": "4.6",
    "reviewCount": "128"
  }
}
```

Only include `aggregateRating` if real reviews are visible on the page. Shipping and return policy details have become meaningful differentiators in shopping surfaces.

### BreadcrumbList

```json
{
  "@context": "https://schema.org",
  "@type": "BreadcrumbList",
  "itemListElement": [
    { "@type": "ListItem", "position": 1, "name": "Ana Sayfa", "item": "https://example.com/" },
    { "@type": "ListItem", "position": 2, "name": "Çözümler", "item": "https://example.com/cozumler/" },
    { "@type": "ListItem", "position": 3, "name": "Bulut Maliyet Yönetimi" }
  ]
}
```

The last item carries no `item` — it's the current page.

### SoftwareApplication / SaaS

```json
  },
  "aggregateRating": { "@type": "AggregateRating", "ratingValue": "4.8", "reviewCount": "42" }
}
```

## The entity graph pattern

Rather than scattering independent blocks across the site, connect them with `@id` so every page reinforces the same entity:

```
https://example.com/#organization      ← the company, defined once on the homepage
https://example.com/#website           ← WebSite, publisher → #organization
https://example.com/yazarlar/x/#person ← each author, worksFor → #organization
https://example.com/blog/y/#article    ← each article, author → #person, publisher → #organization
```

A `WebSite` block with `potentialAction: SearchAction` also declares the site's internal search endpoint.

This costs nothing extra to implement and is the difference between markup that describes pages and markup that describes a business.

## Auditing existing markup

For each sampled page:

1. Extract every `<script type="application/ld+json">` block from the served HTML.
2. Note whether it's in the server response or injected later.
3. Check type correctness, required properties, and duplicate/conflicting blocks.
4. Cross-check each claim against the visible page — does the rating exist? the price? the author?
5. Check `@id` linking, or note its absence as an upgrade opportunity.
6. Report as: current state → what's missing → corrected JSON-LD ready to paste.

Deliver corrected blocks with the user's real values filled in from the page, not placeholder templates. A template the user has to fill in themselves is half a deliverable.
